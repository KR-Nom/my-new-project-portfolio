# GOLABA — 신청 접수와 AI 서류 검수 분리 설계

지원사업 플랫폼 팀 실습에서 백엔드 영역을 담당하며 서비스 경계, REST·Kafka의 역할, 데이터 계약과 저장 범위를 검토한 설계 요약입니다. 제한된 실습 시간 안에 계획했던 백엔드 기능을 모두 직접 완성하지는 못했습니다.

## 해결하려던 문제

신청 요청 안에서 AI 서류 검수가 끝날 때까지 기다리면 긴 모델 처리와 오류가 접수 지연으로 이어집니다. 사용자에게 즉시 필요한 접수 결과와 이후에 처리할 검수 결과를 분리할 필요가 있었습니다.

```text
신청자 → 신청 서비스 → 접수 정보 저장 → 접수 응답
                         ↓
                 Kafka 검수 요청 이벤트
                         ↓
                    AI 문서 검수
                         ↓
                 결과 반영 → 담당자 확인
```

접수 기록을 먼저 남기고 문서 검수는 후속 이벤트로 전달하는 구조를 검토했습니다. 즉시 필요한 조회에는 REST, 처리시간이 긴 후속 작업에는 Kafka를 선택하고, AI가 제시한 근거와 보완 사유의 최종 판단은 담당자가 맡도록 정리했습니다.

## 설계 검토 범위

- 서비스별 역할과 동기 조회·비동기 후처리의 경계
- 화면 용어와 DTO·이벤트·DB 필드가 같은 업무 의미를 가지도록 맞추기
- 서비스 내부 트랜잭션과 서비스 간 이벤트 처리의 차이
- 접수 저장과 외부 처리 실패의 영향을 구분하는 저장 경계
- 서비스별 DB 소유권, 재시도, 실패 이벤트 보관을 후속 단계로 제안

기술 검토에는 Spring Boot, FastAPI, Kafka, REST, Docker Compose와 MariaDB가 포함되었습니다. 원본 실습 구조에는 강의·수강·결제 도메인의 교육 템플릿과 단일 DB가 남아 있습니다. 서비스별 DB 분리와 운영 안정성 개선은 구현 완료 결과가 아닌 발전 방향입니다.

## 검증 범위와 공개 범위

이 문서는 로컬 개인 서브노트와 팀 실습 자료를 바탕으로 작성한 공개용 요약입니다. 신청 응답시간 개선율, 실제 처리량, Kafka 장애 복구 성공률 등 운영 성능을 실측했다는 주장은 하지 않습니다.

전체 교육용 템플릿, 고정 인증 설정, 팀원 정보가 포함된 문서와 제출 PDF는 공개하지 않았습니다. 이 디렉터리는 실행 가능한 완성 서비스가 아니라 담당 범위와 설계 판단을 설명하는 자료입니다.

포트폴리오에는 원본 Vue 소스를 실행한 [랜딩·심사 UI 캡처와 확인 기록](./portfolio-evidence/)을 추가했습니다. 랜딩과 심사 화면의 렌더링을 확인했으며, 화면에 준비 중이라고 표시된 심사 API의 실제 동작을 검증한 것은 아닙니다.
